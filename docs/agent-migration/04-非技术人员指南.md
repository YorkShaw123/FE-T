# 雨生编辑器项目讲义

写给要把它讲出来的人。不用表格，不讲代码，按课件的路子一段段说。

---

## 一、先说这个产品在解决什么

写小说的人有三个麻烦，而且都很具体。

第一个麻烦是设定散着。人物卡在一个文档里，世界观在另一个，前三章的剧情梗概在备忘录，参考的范文在网盘。每次开新章，作者要手工把这些东西翻出来，复制粘贴到对话框里，一遍又一遍。写过二十章之后，光是把"这个人物说话是什么调子"讲清楚，就要花掉一个上午。

第二个麻烦是写出来的东西不像自己。模型很听话，但它默认的文风是那种四平八稳、每段都像总结报告的腔调。作者想要的是短句、留白、对话里带刺，可这些要求写在提示词里，模型只能记住三成。更麻烦的是，作者手上往往有自己写过的东西，或者特别喜欢的某位作家的几段文字，这些才是真正的参照物，但它们太长，塞不进上下文。

第三个麻烦是改一版就丢一版。模型生成一稿，作者嫌 AI 味重，让它重写一遍，第二版好一些，再让它润色，第三版。到最后作者发现还是第一版某一段更好，可第一版已经找不回来了。

雨生编辑器就是为这三个麻烦做的。它把人物、背景、剧情、范例、约束拆成可以复用的模板，你在左边勾一下，它们就按原文进入这次写作；它把你的长篇参考文本切成小片，建成本地索引，等到需要的时候再挑三五个最相关的片段给模型看；它把一次写作拆成七步，每一步的结果都留着，最终的成稿永远可以往前追。

仓库里有一份真实的用户数据可以说明它的用法。一个人导入了十二万字的参考语料，切成了 250 个片段，本地建立了向量索引，然后在一个下午里生成了二十多篇初稿，其中有几篇用上了"风格参考"这一步。这些数字不大，但它说明这个东西是被人真正用起来的，而不是演示完就放在那里。

## 二、为什么写着写着就需要 Agent

课件第一章把这件事分了级，我觉得它分得对。

最底下是提示词工程。你把要求写清楚，模型给你一个回答。再往上一层是工作流，你把几个提示词按固定顺序串起来，第一步的输出喂给第二步。最上面一层才是 Agent，系统自己判断该干什么，自己决定调用哪个工具，走哪条分支。

雨生编辑器现在就停在中间那层。它有一个非常明确的工作流：组装提示词，检查预算，生成初稿，可选地去 AI 味，可选地做风格参考改写，最后落库。这七步是写死的，顺序不会变，唯一的变化是第五步和第六步能不能跳过。

这套东西跑得很好，但它有个天花板。用户对着输入框说一句"这段是不是有点平"，系统接不住。用户说"帮我看看这个人物前后性格对不对"，系统也接不住。它只会一件事，就是生成；它不会判断你想让它干什么。

要去掉这个天花板，缺的不是模型能力，是缺一个"先判断再分发"的层。这个层在课件里叫编排层，写代码的时候叫 Orchestrator，它做的事说白了就三件：听清用户要什么，选一个会做这件事的图，把结果按统一格式吐回去。用户问设定，走问答图；用户要写新章，走写作图；用户要审稿，走审查图；用户一句话里既有写作又有审查，就把两张图串起来跑。

这一步做了，产品的性格就变了。它从一个"生成按钮"变成了一个"写作助手"，因为它们之间的区别不在模型，在于系统知不知道自己在干什么。

## 三、把课件里的知识点一个个落到这个项目上

### 3.1 工程地基：配置、日志、异常、兜底

课件第三章讲的是地基，这部分看着不起眼，但它是整个项目最容易被低估的地方。

配置这块，课件用的是 pydantic 的配置类，好处是所有配置集中在一个文件里，类型不对会在启动时就报错，而不是等到某次调用模型的时候才炸。雨生现在是用一个普通类加环境变量读的，功能上够用，但缺类型校验，比如端口写成字符串这种事要到运行到一半才发现。迁移的时候换掉，成本很低，收益是以后每次改配置都少一次踩坑。

日志这块，现在的代码里散着不少 print，调试的时候能用，上线之后就是噪音。课件用的是结构化的写法，一条日志带着"事件名"和几个键值对，好处是你事后能按 agent 类型、按会话 id 去筛。这个项目文风那一块逻辑很重，出了问题经常要追"这一次检索到底用了哪些片段、分数是多少"，没有结构化日志基本查不动。

异常这块最值得说。现在的代码有一个生成错误类，其余的地方基本靠捕获 Exception 然后翻译成中文。能用，但没法分类。课件把异常分成了可重试和不可重试两类，可重试的是网络抖动、超时、向量库连不上，不可重试的是输入非法、鉴权失败。这个区分不是为了好看，它直接决定了兜底策略怎么展开。

兜底一共三层，这是课件第三章的核心，也是面试里最容易被追问的一段。第一层是重试，隔一秒、再隔三秒，总共三次机会，专门对付那种偶发的网络问题。第二层是降级，三次都失败之后，不是直接报错，而是按业务类型给一个"退而求其次"的结果，比如问答给一句"知识库暂时不可用"，批改给一个"标记为需人工复核"。第三层是系统兜底，所有降级都失效的时候，返回一句人话，保证用户永远能收到响应，界面永远不会一直转圈。

放在雨生这个场景里，这三层的意思很实在。用户按了生成，模型那边超时了。没有兜底的话，界面上那个"生成初稿"的节点会一直显示"正在生成"，用户不知道是卡住了还是在跑。有了兜底，三秒后收到一句"当前模型响应超时，请稍后重试"，而且已经生成的那部分正文会被保存成一条记录，标题后面加个"未完成"。这一点现在的代码里已经做了，迁移的时候不能丢，因为它涉及用户已经付过钱的内容。

### 3.2 State：图里唯一的那份记忆

课件里反复强调一个东西，叫 State。你可以把它理解成一张在整个流程里传阅的病历本。每个环节都在这本子上写一笔，下一个环节翻开来能看到前面写了什么。

为什么非要这样一个东西？因为如果不用它，节点之间就只能靠全局变量或者往数据库里塞临时数据来传话，一旦流程有分支，你就说不清某个值到底是哪条路径写进去的。State 把这件事收拢了：一次请求对应一份 State，流程走完 State 就销毁，中间任何一步都能查。

雨生的写作图，State 里的字段我分成三组。第一组是入参，就是用户在界面上选的那些东西：启用了哪些模板、用哪家模型、开不开去 AI 味、要不要风格参考、这次写作属于什么场景。这一组从进来到出去都不改。第二组是过程数据，组装好的提示词、算出来的预算、检索到的参考片段，这些是中间产物。第三组是产出，初稿、去 AI 味版、风格参考版、最终稿和记录 id。

这么分不是为了整齐。入参组对应的是接口契约，改它等于改前端；过程组是内部实现，随便改；产出组对应数据库字段，改它要写迁移。三组放一起，谁该动谁不该动一目了然。

### 3.3 节点与边：一条流水线变成一张图

课件第二章讲 LangGraph，讲法很朴素：节点是干活的一个函数，边是"干完这个去干那个"，条件边是"看情况去哪个"。

雨生现在是一条直线，七个节点从头走到尾。改造成图之后，同样是这七件事，但每一个都有了名字和位置：组装提示词、检查预算、生成初稿、去 AI 味、检索参考、风格改写、定稿落库。中间有四处分岔。

第一处分岔在预算。算出来这次请求的上下文放不下，就直接中止并告诉用户哪一段超了，而不是硬塞进去让模型自己截断。第二处在初稿之后，如果用户开了去 AI 味就去，没开就跳过。第三处在检索之后，如果这个语料库里找不到合适的片段，就干净地跳过改写，而不是硬着头皮改。第四处是内容为空的时候。

这里有个设计决定值得你记住，因为面试很可能会问到。检索和改写，现在是同一个函数里做的，改成图之后我建议拆成两个节点。原因很简单：检索可能要几百毫秒到几秒，改写要十几秒，把它们捆在一起，一旦检索出问题你没法单独重试；拆开之后，检索能自己重试，检索结果为空时也能直接跳到定稿，不用在改写节点里写一堆 if。

一件小事：图跑起来之后，前端那七个节点的状态是怎么点亮的？靠事件。生成初稿这个节点每吐出一个字，就往前端推一个 token 事件；去 AI 味开始和结束各推一个状态事件；检索完成推一个带"选中了几个片段"的事件。这层约定是前后端之间最脆弱的地方，改它要同步改前端的十九个脚本，所以我在设计文档里单独列了一张对照，谁推什么事件、点亮哪个节点，写死。

### 3.4 编排器：一次请求该走哪张图

课件第八章讲编排，讲了两件事：一是统一入参出参，二是单 Agent 直达和多 Agent 串联。

统一入参出参这件事，说白了就是所有请求进来都穿同一件衣服。不管你是来写文章的还是来问设定的，请求里都有这么几个字段：谁发的、哪个会话、要干什么、说了什么、附带了什么上下文。出去的响应也统一：成不成、哪个 Agent 处理的、主要文本、结构化结果、有没有走降级、错误信息是什么。这样前端只认一套格式，加一个新 Agent 不用动前端。

雨生改造之后有三张图。写作图负责写，风格问答图负责答疑找参考，一致性审查图负责挑毛病。用户说"接着上一章写"，编排器判断这是写作，直接把上一次的记录和设定塞进写作图的入参里。用户说"这段帮我看看"，判断是审稿，走审查图。用户说"写完顺便帮我看看有没有前后矛盾"，这就是串联了，写作图跑完把记录 id 交给审查图，一次请求两件事都办了。

中间还有一条路叫澄清。用户的输入既不像写作也不像提问，比如就一句"嗯？"，这时候不该硬猜，应该反问一句，同时给出三个可点的选项。课件里那条 clarify 分支就是干这个的，很多实现会偷懒把它省掉，省掉的代价是用户第一次用会觉得系统在乱答。

### 3.5 检索：为什么不能把资料直接塞进提示词

课件第五章讲 RAG，讲了整整一章。核心其实一句话：上下文有限，而资料是无限的，所以要先挑再给。

雨生的语料库是十二万字，切成了 250 片。为什么不直接全塞进去？因为十二万字大概六七万 token，塞进去之后模型就没有余量写正文了，而且中间那段内容模型基本会忽略，这是很早就被验证过的现象。所以必须检索。

检索这件事，课件讲了三层。第一层是切片，怎么切很有讲究：切太碎语义不完整，切太大检索不准。雨生是按段落为主、超长段落再切，目标四百字上下。第二层是召回，用两路。一路是向量，把问题和片段都变成一串数字，算相似度，擅长"意思相近但用词不同"；另一路是关键词，用 BM25 这类统计方法，擅长"这个词必须出现"。两路结果用 RRF 融合，就是把两边排名倒数相加再排序，简单但有效。第三层是重排，把召回的十几个候选再用更贵的模型逐个打分，取前三五个。

雨生在这个基础上多做了一件事，叫内容泄漏惩罚。因为它的参考文本本身就是要模仿的原文，如果检索回来的片段和用户正文里的句子高度重合，那改写出来就是抄。所以它在打分的时候会把"和原文重合多少"算进去，重合度高的片段直接压分。这是课件里没有的东西，也是这个项目在文风这块真正花了心思的地方。你要能讲清楚这一条，因为它说明你不是照抄教程。

还有一层是意图分类。课件第五章把问题分成四档：精确的、模糊的、宽泛的、跟知识库无关的。精确的直接检索；模糊的先让模型猜一个假想答案再拿去检索，这叫 HyDE；宽泛的先改写成几个不同角度的问题分别检索，再合并；无关的直接让模型自由回答，别去检索里搅和。这四档分开处理，比一律检索效果好得多，因为不同问法需要不同的检索策略。

雨生现在的实现里没有这么细的分档，改造时补上。但要清楚，补这一层的目的不是炫技，是因为"帮我找一段像这样的描写"和"这个人物的口头禅是什么"本来就是两种问题。

### 3.6 人在回路：什么时候该停下来问人

课件第六章讲试卷批改，里面有一步叫 Human-in-the-Loop，意思是机器跑到一半停下来，把判断交给老师确认，老师改完再继续。

这个机制搬到写作工具上，最自然的落点有两个。

一个是预算警告的时候。算出来这次最多能写八千字，但用户想要一万二。系统可以直接截断，也可以停下来问一句：是继续（可能被模型截断），还是把输出缩短到八千字以内保证完整？这个问题的答案只有用户知道，替他做决定都是错的。

另一个是用户中途点停止的时候。停止不是一个错误，是一个决定。已经生成的三千字要保存下来，标题加个"未完成"，备注写清楚原因。这个动作现在就在做，迁移到图里之后要用中断机制重新实现一遍，别弄丢。

课件里还有一种用法是审查环节的人工确认，比如一致性审查图跑完，发现三处矛盾，用户可以逐条勾选"这条我认"或者"这条忽略"。这属于锦上添花，有余力再做。

### 3.7 流式：为什么不能等全部生成完再返回

课件第二章讲 FastAPI 的时候顺带讲了 SSE，第九章讲前端集成又提了一次。这件事非技术的人也得懂个大概，因为它是体验的分水岭。

模型写一千五百字要四十秒。如果不流式，用户按了按钮，四十秒里界面什么都不动，大部分人会以为卡死了，然后刷新页面，然后钱白花了。流式的做法是每生成几个字就往前端推一段，用户看着文字一行行出来，四十秒就变成了"它在写"而不是"它死了"。

技术上这叫 Server-Sent Events，就是浏览器和服务器之间开一条单向的管道，服务器有问题就往下推。雨生现在用的就是它，前端用 fetch 拿到一个流，逐行解析。

这里有个细节容易被忽略：流式不只是为了好看，它还承担状态同步。七个节点里哪个在做、哪个做完了，全靠这条管道上的事件。所以事件的命名和顺序是一种契约，不是随手写的。

## 四、迁移之后，系统长什么样

一句话：壳没变，里面的骨架换了。

壳指的是外壳和界面。Tauri 窗口、双击即用、本地 SQLite、离线可用、一个四十兆的安装包，这些都不动。用户看到的还是那四个页签，工作台还是那七个节点。

骨架换了三样东西。第一样是服务方式，从 Flask 的同步处理换成 FastAPI 的异步处理，这样生成一篇文章的时候，用户还能切到文风管理页去导入语料，两个请求互不排队。第二样是组织结构，从"路由 + 服务"两层，变成"接口层、编排层、Agent 层、公共层、数据层"，每一层的职责写死在文档里，谁都不许越界。第三样是有了一组共用的零件：模型工厂负责按用途分配模型并缓存，重试模块负责三层兜底，记忆模块负责多轮对话的上下文，知识库接口负责屏蔽"底下到底是 SQLite 还是 Milvus"。

有一点要提前想清楚，也是这次改造里最需要判断力的地方。课件用的那套基础设施是给服务器准备的：PostgreSQL、Milvus、MinIO、etcd，还有三个加起来四点五个 G 的模型。这些东西在机房服务器上很合理，但装不进一个面向普通用户的 Windows 桌面程序。硬搬的结果是安装包从四十兆涨到五个 G，用户还得先装 Docker。

所以我的方案是把架构对齐，把选型换掉。数据库仍然用 SQLite，但换成异步驱动，写法与课件一致；向量检索仍然用 SQLite 加 numpy，但包成一个统一的知识库接口，将来真要做云端版，换一个实现就行；嵌入模型仍然用它现在那个只有几十兆的 ONNX 小模型，需要更强的效果时再挂 BGE-M3。这三处替换不是妥协，是把"桌面优先"这个产品定位当成约束条件来做设计。面试里如果被问"为什么不照抄课件的技术栈"，这就是标准答案。

## 五、面试里大概率会问的七个问题

**第一个，你这套和直接调模型的接口有什么区别。**
区别在于系统知不知道自己在干什么。直接调接口，是我给模型一段话，模型还我一段话，出了问题我什么都不知道。这套东西里，每一次调用都在一个有名有姓的节点里，前面有预算检查，后面有质量检查，中间有重试和降级，跑完之后有一条记录能追。而且你问它"这段平不平"，它会先去检索参考、再去判断，而不是硬着头皮生成一段。

**第二个，为什么要用 LangGraph，自己写 if else 不行吗。**
简单的流程确实用 if else 就行，雨生现在就是。但流程一旦有分支、有并行、有中断、要恢复，手写会迅速失控。LangGraph 给的是四件东西：状态怎么合并、分支怎么表达、并行怎么跑、中断点怎么存。特别是并行，一致性审查那四个维度要同时跑，手写就是开四个线程自己收回结果，还得处理其中一个失败怎么办。用图的话，这一层是现成的。

**第三个，为什么要用大模型做意图分类，不用小模型。**
课件里其实两种都有。用大模型的好处是不用训练、改分类口径只改提示词、跨场景泛化好；坏处是慢一点、贵一点。但在这个产品里，意图分类的调用频率很低，一次对话才一次，贵不到哪去。小模型适合那种每秒几百次的场景，比如搜索框的联想。所以这是个成本判断，不是技术优劣。可以补一句：如果以后要做高频路由，把本地那个八十多兆的分类器接进来，接口是现成的。

**第四个，为什么检索要放在本地，不用向量数据库。**
两个原因。一是部署，Milvus 这种系统要 etcd 和对象存储配合，桌面程序装不下。二是数据，用户的语料是他自己的作品，不上传才是对的。代价是检索能力弱一些，十万级片段用 numpy 算余弦完全够，百万级才会吃力。这个取舍说得清楚，比说"我们用了向量数据库"更值钱。

**第五个，三层兜底真的有用吗，还是写着好看。**
有用，而且是被真实故障逼出来的。第一层解决的是一秒钟的网络抖动，没有它，用户会因为一次抖动重按一次按钮，多花一次钱。第二层解决的是模型服务整体不可用，这时候不该让用户干等，应该给出"这一部分先跳过，其余照常"的结果。第三层解决的是意料之外的错误，保证界面不会永远转圈。三层各管一段，不是重复劳动。

**第六个，你怎么评估这套系统好不好。**
分三层。模型层看生成质量，人工打分加抽样；系统层看成功率、首次响应时间、降级触发率，这些从日志里算；业务层看用户改稿的比例、采纳率、重生成率。文风这块还有额外一层，用固定语料跑基准测试，比较改造前后检索结果的排序是否一致，这是防止"重构把算法改坏"的唯一硬办法。

**第七个，这个项目里最难的部分是什么。**
诚实地说，是把一条写死的流水线拆成图，还要保证每一步的行为跟原来一模一样。因为原来那八百多行代码里藏着很多隐式约定，比如什么时候推状态事件、什么情况下保存未完成的稿子、检索失败怎么跳过。这些东西不在文档里，只能一行行读出来，再在新结构里重新表达一遍。拆的过程比写新的难。

## 六、如果要写进简历

简历上的项目描述最忌讳两种写法：一种是罗列技术名词，一种是复述功能列表。好的写法是动词开头，说清楚你做了什么、解决了什么问题、结果是什么。

可以参考这样的句子：把写作流程从固定顺序的单体服务改造为基于状态图的 Agent 架构，拆出写作、风格问答、一致性审查三张图并加了一层编排路由，使系统能处理"帮我看看这段"这类开放式请求，而不是只能响应生成指令。

也可以这样写：为本地文风检索设计了混合召回与内容泄漏惩罚机制，在没有向量数据库的桌面环境下用 SQLite 加 numpy 实现两路召回与重排，把参考片段与原文的重合度纳入打分，避免改写变成抄袭。

如果篇幅允许，再加一句讲取舍：在保持四十兆安装包的前提下放弃了服务端组件，改用适配器隔离存储与向量实现，为将来的云端版本留出替换点。

这三句话里没有一个是空话，每一个都能被追问三层。这就是能写进简历的样子。

## 七、最后

这套东西的价值，不在于用了多少框架。框架会换，今天是 LangGraph，明年可能是别的。

它真正的价值在于把一次不确定的模型调用，变成了一个可以观察、可以中断、可以回退的流程。模型仍然会说错话、会超时、会写出不像人写的东西，但系统知道它在哪一步出错、错了之后退到哪里、退完之后怎么告诉用户。

一个写小说的人不需要懂这些。他只需要按一下生成，看着字一行行出来，不满意就改，改坏了还能找回上一版。这中间所有的编排、路由、兜底、检索，都是为了让他不必知道。

能把这件事讲清楚，你也就把这个项目讲清楚了。
