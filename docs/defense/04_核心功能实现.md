# 任务四：核心功能实现

## 功能总览

Flora Editor 共有 **6 个核心功能**，按调用关系分层：

```
                        ┌──────────────────┐
                        │   ⑥ 桌面启动      │
                        │  (Tauri Sidecar)  │
                        └────────┬─────────┘
                                 │ 拉起
                                 ▼
┌─────────────┐  选用  ┌──────────────────┐
│ ① 模板管理   │ ────► │  ② 文章生成       │ ◄── 联动 ── ③ Style RAG 语料检索
│ (素材仓库)   │       │  (核心枢纽)       │
└─────────────┘       └────────┬─────────┘
                               │ 产出
                               ▼
                      ┌──────────────────┐        ┌──────────────────┐
                      │ ④ 生成记录管理    │        │ ⑤ Style Card 分析 │
                      │ (创作档案)       │        │ (文风画像)        │
                      └──────────────────┘        └──────────────────┘
```

## 功能一：模板管理（素材仓库）

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 前端 | `static/js/templates.js` | 模板列表渲染、创建/编辑表单、版本历史弹窗 |

## 功能二：文章生成（核心枢纽）

这是全项目最复杂的功能，采用 **SSE 流式输出 + 六阶段流水线**。

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 前端 | `static/js/generation.js` | 参数面板、ReadableStream 逐字渲染、阶段进度条 |
| 路由 | `routes/generation_routes.py` | `/generate-stream` SSE 端点 |
| 服务 | `services/generation_service.py` | 流水线编排（下述六阶段） |
| 编排 | `services/prompt_assembler.py` | 模板 → 结构化 messages |
| 检索 | `services/style_rag_service.py` | 风格片段检索（联动功能三） |
| 适配 | `services/llm_adapter.py` → `api_client.py` | 8 家厂商协议统一 |
| 守卫 | `services/operation_guard.py` | 并发互斥（同一时刻仅一个模型操作） |
| 数据 | `GenerationRecord` | 落盘生成记录（联动功能四） |

### 时空图（六阶段流水线）

```
用户         前端JS          Flask路由        generation_service        LLM厂商API
 │            │                │                   │                     │
 │ 点击生成    │                │                   │                     │
 ├───────────►│ POST /generate-stream               │                     │
 │            ├───────────────►│                   │                     │
 │            │                │ 建立 SSE 连接      │                     │
 │            │◄─ status事件 ──┤                   │                     │
 │            │                ├──────────────────►│                     │
 │            │                │                   │                     │
 │ ① 状态提示 │                │  [阶段1] 组装提示词 │                     │
 │◄───────────┤◄─ status ──────┤  模板→messages     │                     │
 │            │                │                   │                     │
 │            │                │  [阶段2] 初稿生成   │                     │
 │ ② 逐字显示 │                │                   │ POST /chat (流式)    │
 │ 初稿文字    │◄─ content事件 ─┤◄──────────────────┤◄────────────────────┤
 │◄───────────┤  (多次增量)     │                   │  delta...delta...   │
 │            │                │                   │                     │
 │            │                │  [阶段3] RAG检索    │                     │
 │ ③ 提示注入 │                │  联动Style RAG:    │  (本地计算,无网络)    │
 │ 风格参考    │◄─ status ──────┤  检索Top-4片段     │                     │
 │◄───────────┤                │                   │                     │
 │            │                │  [阶段4] 风格重写   │                     │
 │ ④ 显示重写 │                │                   │ POST /chat          │
 │ 版本       │◄─ content事件 ─┤◄──────────────────┤◄────────────────────┤
 │◄───────────┤                │                   │                     │
 │            │                │  [阶段5] 去AI味    │                     │
 │ ⑤ 去AI味  │                │  (若开启)          │ POST /chat          │
 │ 处理       │◄─ content事件 ─┤◄──────────────────┤◄────────────────────┤
 │◄───────────┤                │                   │                     │
 │            │                │  [阶段6] 落盘      │                     │
 │            │                │  写GenerationRecord│                     │
 │ ⑥ 完成     │◄─ complete事件 ┤  (含各阶段版本)    │  → SQLite           │
 │◄───────────┤  + done        │                   │                     │
```

**关键设计**：

1. **SSE 先连接、后干活**——`sse_events()` 生成器先 yield 状态事件建立连接，再执行耗时的 RAG 检索和 Prompt 组装，避免前端长时间无响应误判为超时。
2. **六阶段流水线**——初稿(阶段2)只组装模板与 Style Card；风格参考(阶段3-4)在初稿完成后单独执行，RAG 检索不阻塞首字输出。
3. **operation_guard 并发守卫**——`acquire_model_operation()` 保证同一时刻只有一个模型调用在执行，防止用户连点导致请求风暴。
4. **一份记录存多个版本**——`complete` 事件携带 `first_content`（初稿）、`deai_content`（去AI味）、`style_rewrite_content`（风格重写）、`final_content`（最终版），前端可对比查看。

## 功能三：Style RAG 风格语料检索

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 前端 | `static/js/style_rag.js` | 语料库管理、导入进度条、检索测试面板 |
| 路由 | `routes/style_corpora_routes.py` | 语料 CRUD + 向量化索引 + 混合检索 |
| 服务 | `services/style_rag_service.py`（591行） | 分句→向量化→混合检索 |
| 进度 | `services/style_index_progress.py` | 索引进度追踪（分块反馈） |
| 数据 | `StyleCorpus` / `CorpusChunk` | 语料元信息 + 分块向量 |

### 时空图

```
用户            前端JS           Flask路由          style_rag_service        SQLite
 │               │                │                    │                     │
 │ 导入参考小说   │                │                    │                     │
 ├──────────────►│ POST 语料文本    │                    │                     │
 │               ├───────────────►│ import_corpus_text │                     │
 │               │                ├───────────────────►│                     │
 │               │                │                    │ 创建语料记录         │
 │               │                │                    ├────────────────────►│
 │               │                │                    │ 分句(中文标点感知)    │
 │               │                │                    │ 滑窗切块(~500字)     │
 │               │                │                    │ 本地向量化          │
 │               │  进度回调        │                    │   (ONNX/特征向量)    │
 │◄──────────────┤◄─ 进度事件 ─────┤◄───────────────────┤                     │
 │               │                │                    │ 批量写入块+向量      │
 │               │                │                    ├────────────────────►│
 │ 导入完成 ✓    │◄───────────────┤◄───────────────────┤                     │
 │◄──────────────┤                │                    │                     │
 │               │                │                    │                     │
 │ (生成时自动触发)│                │ hybrid_search()    │                     │
 │  ── 联动功能二 ─┼───────────────┼───────────────────►│                     │
 │               │                │  风格指纹 vs 全库  │                     │
 │               │                │  BM25 + 向量 余弦   │                     │
 │               │                │  → Top-4 片段      │                     │
 │               │                │◄───────────────────┤◄────────────────────┤
```

**关键设计**：**混合检索**（BM25 关键词 + 向量语义余弦相似度加权融合），比单一向量检索对中文短句更准确。向量计算默认走本地特征（无网络依赖），符合"Style Engine 默认完全本地"的项目约束。

## 功能四：生成记录管理（创作档案）

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 前端 | `static/js/records.js` | 记录列表、多版本对比视图、全屏编辑 |
| 路由 | `routes/generation_routes.py`（records 段） | 分页列表 / 单条 / 更新 / 删除 / 清空 |
| 服务 | `services/generation/records.py` | 记录 CRUD + 排序分页 |
| 数据 | `GenerationRecord` | 含六个内容版本字段 |

### 时空图（简）

```
用户 → 前端JS → GET /api/generation/records?page=1
                        │
                        ▼
              records.py: 分页查询（按时间倒序）
                        │
                        ▼
              返回 [{id, title, final_content, 模型, tokens, 时间}...]
                        │
                        ▼
        前端渲染列表 → 点击记录 → 版本对比视图
        (初稿 vs 去AI味 vs 风格重写 vs 最终版)
```

**关键设计**：每条记录保留**完整版本链**（初稿/重写/去AI味/最终版），创作者可回看 AI 每一步干预的痕迹——这既是"创作档案"，也是对 AI 修改的可审计记录。

## 功能五：Style Card 文风分析

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 前端 | `static/js/style_card.js` | 分析按钮、文风卡片展示、人工编辑 |
| 路由 | `routes/style_routes.py` | 获取/分析/刷新/恢复 Style Card + 片段管理 |
| 服务 | `services/style_profile_service.py` | LLM 分析 + 本地 44 特征（style_feature_service.py） |
| 数据 | `StyleProfile` / `StyleExcerpt` | 文风卡片 + 精选片段 |

### 时空图（简）

```
用户指定"范例文章"模板 → 点击[分析文风]
        │
        ▼
POST /api/style-profiles/5/analyze
        │
        ▼
style_profile_service:
  ├─ 本地分析: style_feature_service 计算 44 个统计特征
  │    (句长分布/标点习惯/词汇丰富度/对话比例/段落节奏...)
  │    ↓ 生成 Style Card（JSON）
  └─ 可选: LLM 增强描述（需 API Key）
        │
        ▼
存入 StyleProfile 表（含 source_hash 指纹）
        │
        ▼
生成时（功能二阶段1）自动注入启用的 Style Card
  → 模型按目标文风写作
```

**关键设计**：`source_hash` 机制——范例文章内容变化后，Style Card 自动标记 `is_stale: true` 提示重新分析，防止用旧画像指导新文风。

## 功能六：桌面启动（Tauri Sidecar）

### 前后端逻辑链路

| 层 | 组件 | 职责 |
|----|------|------|
| 壳 | `src-tauri/src/lib.rs`（177行 Rust） | 窗口管理、Sidecar 进程生命周期 |
| 打包 | `flora-server.spec`（PyInstaller） | Flask → 单文件 `flora-server.exe` |
| 服务 | `server/app.py` → `create_app()` | 应用工厂、蓝图注册、安全头 |

### 时空图（简）

```
用户双击 雨生编辑器.exe
        │
        ▼
Tauri Rust 壳启动
  ├─ 1. spawn Sidecar: 启动 flora-server.exe (Flask)
  ├─ 2. 等待 /api/health 返回 ok (健康检查轮询)
  ├─ 3. 创建 WebView 窗口, 加载 http://127.0.0.1:5000
  └─ 4. 监听窗口关闭 → kill Sidecar 进程 (不留孤儿进程)
        │
        ▼
  用户在原生窗口中使用全部功能（功能一~五）
        │
        ▼
用户关闭窗口 → Rust 壳清理 Sidecar → 进程树全部退出
```

**关键设计**：**进程生命周期绑定**——Sidecar 的存活严格跟随主窗口，关闭窗口即清理全部子进程，不留后台残留（本地工具的基本素养）。

## 联动闭环说明

三条最重要的功能联动闭环：

| 闭环 | 路径 | 业务价值 |
|------|------|---------|
| **创作闭环** | 生成(②) → 记录(④) → 满意的段落回写为模板(①) → 下次生成复用 | 提示词资产越用越厚 |
| **文风闭环** | 范例文章 → Style Card(⑤) + 语料库(③) → 生成时双路注入(②) | AI 写出"像你"的文字 |
| **质量闭环** | 初稿 → 风格重写 → 去AI味 → 版本对比(④) → 人工定稿 | 每一步 AI 干预可审计、可回退 |
