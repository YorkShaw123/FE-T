## Q1：你为什么选择 Tauri 2 + Flask 这个技术栈，而不是更主流的 Electron + Node.js？

**参考应答：**

选择 Tauri 2 + Flask 主要基于三个考虑：

1. **安装包体积**。Electron 捆绑完整 Chromium，安装包动辄 80MB 以上；Tauri 使用 Windows 系统自带的 WebView2，外壳仅 3~5MB。Flask 后端用 PyInstaller 打包后约 15MB，总体积控制在 20MB 以内，适合作为"小工具"分发。

2. **Python 生态对齐**。本项目的核心能力——Style Engine 文风分析、NumPy 矩阵运算、SQLite 操作、中文 NLP 处理——全部是 Python 强项。如果用 Node.js 后端，要么引入 Python 子进程增加复杂度，要么用 JS 重写全部算法，得不偿失。

3. **Sidecar 架构解耦**。Tauri 通过 `externalBin` 把 Flask 打包后的 `flora-server.exe` 作为 Sidecar 分发。Tauri 负责窗口和生命周期管理，Flask 负责全部业务逻辑，两者通过 HTTP 通信。这样后端可以独立调试（浏览器访问 127.0.0.1:5000），也可以独立复用。

**追问：Tauri 的 Sidecar 生命周期管理具体怎么做的？**

Rust 端在 `lib.rs` 中做了几件事：启动时用 `pick_free_port()` 绑定空闲端口，通过 `FLORA_PORT` 环境变量传给 Sidecar 进程；然后 `wait_for_server()` 以 100ms 间隔轮询端口，最多等 60 秒；就绪后导航窗口。退出时先发 `POST /api/system/shutdown` 让 Flask 优雅退出（响应后延迟 150ms 自行 `_exit(0)`），再清理子进程树。如果后端已不可达则静默忽略。

**追问：为什么 Flask 要自己实现退出逻辑，不直接让 Tauri 强杀？**

因为强杀会导致 SQLite WAL 文件未正常 checkpoint，数据库可能残留 `-wal` 和 `-shm` 临时文件。让 Flask 在 HTTP 响应发出后自行退出，确保当前请求处理完毕、数据库连接正常关闭。

**追问：路由层和服务层的边界怎么划分的？**

路由层只做三件事：解析 HTTP 请求参数、调用对应的 service 函数、把结果序列化为 JSON 或 SSE 返回。领域算法（提示词组装、文风检索、Token 预算计算）全部在 service 层。这样可以保证：如果未来换一套 HTTP 框架（比如换成 FastAPI），service 层代码可以原样复用。

**追问：为什么前端不用框架？**

前端是单页工作台，核心交互是工作流画布（7 个节点的拖拽连线）、模板列表、编辑器和设置面板。用原生 JS + 模块化拆分（16 个 .js 文件，各自管理一个功能区域）足够了。不引入框架的好处是：不需要 Node 构建链、不需要维护 lock 文件、桌面版和浏览器调试复用同一套静态文件、Tauri 打包时直接 PyInstaller 把 static 目录打进去。

## Q3：你的 API Key 安全设计是怎么做的？为什么不在数据库里存一份方便用户下次使用？

**参考应答：**

API Key 的安全设计遵循一个原则：**只在当前请求的内存中存在，请求结束即销毁**。具体措施：

1. 用户在前端输入框填写 Key，通过 `fetch` 请求体传给后端
2. 后端从请求中取出 Key，构造 `LLMClient(provider, api_key)` 实例
3. 调用完 LLM API 后，函数返回，Python GC 回收 client 实例
4. Key 不写入 SQLite、不写入文件、不写入 `localStorage`、不写入日志
5. 重新打开应用后需要再次输入

为什么不存？因为这是本地桌面工具，用户数据目录 `%USERPROFILE%\.flora-editor\` 中只有一个 `flora.db`。如果把 8 家服务商的 Key 都存进去，一旦数据库泄露（比如用户共享了数据目录、备份到云盘），所有 Key 一起暴露。现在的设计下，即使数据库被完整拷走，里面也没有任何 Key。代价是用户每次打开要重新输入，但这是个安全换隐私的合理取舍。

**追问：那用户每次打开都要重新输 Key，体验不好怎么办？**

可以引入系统级密钥管理（Windows Credential Manager），通过 Tauri 的 Rust 端调用系统 API 存取 Key，Flask 端永远不接触明文。但这需要额外设计和实现，当前版本以安全优先。

## Q4：Style Engine 的 44 个文风特征具体是什么？为什么选择本地分析而不是直接用 Embedding？

**参考应答：**

Style Engine 的 44 个特征分为几大类（定义在 `STYLE_FEATURE_V1.md` 中，已在 M1 里程碑冻结）：

| 类别 | 示例特征 | 设计原因 |
|------|---------|---------|
| 句长与节奏 | 平均句长、短句占比、句长方差 | 中文长句堆叠是 AI 生成的典型特征 |
| 标点习惯 | 逗号密度、句号密度、省略号频率、破折号使用 | 标点节奏是人类作者的肌肉记忆，AI 难以模仿 |
| 功能词 | 连词密度、语气词频率、代词分布 | "然而"、"总之"等词的过度使用是 AI 味的根源 |
| 基础句法 | 对白密度、段落长度分布、独立成段比例 | 对话占比和段落切分方式因作者而异 |
| 语言组织 | 修饰语密度、动词-名词比、重复 N-gram | 反映行文密度和遣词习惯 |

为什么不用 Embedding 替代？因为 Embedding 是黑盒——你拿到一个 1024 维向量，知道两个文本"相似"，但不知道**为什么**相似、相似在哪个维度。Style Engine 的特征是可解释的：检索结果会附带 `explain_style_feature_matches()`，告诉用户"这个片段的句长分布、对白比例和标点节奏与当前写作场景匹配"。这种透明度对于写作辅助工具很重要——用户需要理解为什么推荐这个参考片段。

此外，Embedding 需要远程 API 调用（或本地 ONNX 模型），而 Style Engine 的 44 个特征用纯 Python 正则和统计就能算完，零依赖、零网络、零隐私风险。

**追问：那 Embedding 在你的系统里是什么角色？**

是可选的辅助信号。检索排序公式是 `final_retrieval_score = style_score × 0.7 + semantic_score × 0.3`（权重为示意）。没有 Embedding 时，semantic_score 为 0，纯靠 Style Engine 的本地特征排序。有 Embedding 时，语义相似度作为加分项提升召回率。两者通过 RRF（Reciprocal Rank Fusion）融合，而不是简单加权——这样即使某一路信号缺失，另一路仍能独立排序。

## Q5：你的 Style RAG 检索流程是怎样的？如何防止把原文内容直接复制进生成结果？

**参考应答：**

Style RAG 的检索流程分两条链路并行计算后融合：

```
链路 A（向量语义）：
  当前写作上下文 → Embedding → 与语料库所有 chunk 向量做余弦相似度 → Top-N

链路 B（关键词 BM25）：
  当前写作上下文 → FTS5 trigram 查询 → BM25 排序 → Top-N

融合 → RRF(Reciprocal Rank Fusion) → 内容复用惩罚 → MMR 多样性重排 → 3~5 个片段
```

防止原文复用是设计的核心约束，有三道防线：

1. **内容复用惩罚（Content Leakage Penalty）**：检索时计算 `content_leakage_metrics()`，检查关键词重叠、字符 N-gram 重叠和连续长字符串重合。如果某个片段与当前上下文的内容重合度过高（比如相同的人物名、地名、独特表达），会降低其排序分。

2. **Prompt 级约束**：注入提示词的不是"参考这些内容来写"，而是"这些片段的**文风**（句式、节奏、标点习惯）是你的参考标准，不得照抄其中的人物、地点、情节或独特句子"。`STYLE_STRENGTH_CONSTRAINTS` 中明确定义了 light/medium/strict 三档约束文本。

3. **检索用途区分**：Style RAG 检索的是"文风参考片段"，不是"知识问答片段"。这正是 RAG 在本项目中的特殊用法——RAG 通常用于检索世界知识注入上下文，这里用于检索**写作风格**注入**二次改写**指令，且只取当前 chunk 的原文注入。

**追问：FTS5 的 trigram tokenizer 对中文有什么问题？**

trigram 要求至少 3 个连续字符才能匹配，2 字词会被忽略。所以我在 `SCENE_FALLBACK_QUERIES` 里把场景标签展开为多个 4 字短语（如 "他说道"、"她笑道"），而不是直接用 "对话" 这种 2 字词查询。这是一个工程妥协——trigram 对中文不完美，但 SQLite 内置支持，不需要额外依赖 jieba 分词。

## Q6：你的 LLM 适配层是怎么处理不同厂商协议差异的？

**参考应答：**

不同厂商虽然都声称兼容 OpenAI 协议，但实际有大量细节差异。`LLMAdapter` 和 `api_client.py` 中做了几层适配：

1. **思考模式协议差异**：不同厂商的 thinking 参数名和返回格式不同。配置中为每个 Provider 指定 `thinking_protocol`：
   - `thinking_object_with_effort`（DeepSeek）：请求带 `reasoning_effort`，响应 `reasoning_content` 在独立字段
   - `thinking_object`（Kimi/智谱）：请求带 `thinking` 对象，响应类似
   - `enable_thinking`（硅基流动）：布尔参数
   - `gemini_effort`（Gemini）：思考不可关闭，`thinking_budget` 控制

2. **采样参数过滤**：`LLMAdapter.normalize_sampling()` 按每个 Provider 声明的 `sampling_params` 过滤。比如 DeepSeek 的思考模式下 temperature 和 top_p 不生效，发过去也没意义；frequency/presence penalty 已被官方废弃。过滤后返回 `sampling_dropped` 告知用户哪些参数被丢弃了。

3. **API Key 格式兼容**：用户可能从文档复制 `Bearer <TOKEN>` 格式的 Key，`LLMClient` 统一剥离 `Bearer ` 前缀再加回去，避免双重 Bearer。

4. **思维链兜底**：有些模型不遵守协议，把正文混入 `reasoning_content` 返回，`content` 为空。`_story_content_is_empty()` 检测这种情况，自动把 `reasoning_content` 回显到正文区并标记 `reasoning_fallback = True`。

**追问：为什么不直接用各厂商的官方 SDK？**

8 家厂商就是 8 个 SDK，每个都带自己的依赖树（httpx、pydantic、各种版本冲突）。用标准库 urllib 统一实现 OpenAI 兼容协议，零额外依赖，PyInstaller 打包体积直接少了几十 MB。代价是需要自己处理 SSE 流式解析和协议差异，但这些逻辑在 `LLMAdapter` 里集中管理，可维护性不差。

## Q7：你提到数据库迁移使用"幂等迁移机制"，这是什么意思？

**参考应答：**

`migrations.py` 中的迁移是幂等的——即多次执行结果与一次执行相同。每个迁移步骤先检查当前 schema 是否已经满足条件（比如表是否存在、列是否已添加），满足则跳过，不满足才执行 ALTER/CREATE。

这样做的原因：用户可能从很早的版本升级上来，也可能中间跳过几个版本。幂等迁移不依赖版本号顺序，每个步骤独立检查"是否需要做"，而不是"从版本 X 迁移到版本 Y"。这比 Django/SQLAlchemy 的线性 migration chain 更简单，也不需要维护版本号表。

**追问：首次启动时数据迁移做了什么？**

`_migrate_legacy_data()` 在 `app.py` 中调用，处理品牌更名和数据目录迁移：如果统一数据目录 `~/.flora-editor/data/flora.db` 不存在，但旧版项目内 `data/` 目录有数据库文件，就复制过去（不移动，保留原文件作为备份）。这保证了用户从旧版本升级时数据不丢失。

## Q8：你用了 AI 编程工具来开发这个项目，能谈谈具体的工作方式吗？

**参考应答：**

项目主要使用 Trae + DeepSeek V4 Pro 和 VSCode + Codex 插件两种 AI 编程方式。工作流是"vibe coding"模式：

1. **架构设计阶段**（文档驱动）：先写 `AGENTS.md` 和 `docs/style-engine/EXEC_PLAN.md`，定义约束和里程碑。把设计文档喂给 AI，让它理解全局约束后再逐模块实现。

2. **功能实现阶段**（分模块推进）：每个功能模块单独跟 AI 对话。先描述功能意图和边界条件，AI 生成初版代码，我审查后接受或要求修改。比如 Style Engine 的 13 个里程碑就是逐个推进的——M1 冻结特征定义后，M2 才开始实现提取器，每个里程碑有明确的验收标准。

3. **测试与修复阶段**（截图驱动）：遇到 bug 时上传截图和报错信息，AI 定位问题后给出修复方案。比如前端工作流画布的节点连线 bug，就是通过截图定位的。

4. **代码审查阶段**（交叉验证）：用不同 AI 工具交叉检查。Trae 生成的代码用 Codex 审查，反之亦然，利用不同模型的盲区互补。

关键经验：AI 生成代码不能直接用。每次都要理解它做了什么、为什么这样做，确保自己能解释每一行。AGENTS.md 里的约束就是给 AI 的"护栏"——告诉它什么不能改、什么必须保持兼容。

## Q10：相比 GitHub 上其他 AI 写作工具，你的项目有什么创新点？

**参考应答：**

GitHub 上主流的 AI 写作工具大致分几类，本项目在以下方面有差异化：

| 对比维度 | 常见 AI 写作工具 | Flora Editor |
|---------|-----------------|--------------|
| 运行形态 | Web SaaS 或 VSCode 插件 | 纯本地桌面 EXE，数据不出本机 |
| 提示词管理 | 单一 Prompt 输入框 | 5 类模板分类管理 + 版本控制 + 按需启用 |
| 文风控制 | 无，或依赖"few-shot 示例" | 本地 Style Engine（44 个可解释特征）+ Style RAG 语料检索 |
| 内容复用保护 | 无 | 三道防线：Content Leakage Penalty + Prompt 级约束 + 检索用途区分 |
| 去AI味 | 无或简单后处理 | 可选二阶段链路：去AI味 → Style RAG 风格参考二次改写 |
| LLM 适配 | 单一厂商绑定 | 8 家 Provider 统一适配，协议差异透明处理 |
| 向量检索 | 依赖 FAISS/Chroma | 纯 NumPy 矩阵运算 + SQLite BLOB，零额外依赖 |

**核心创新点：**

1. **Style Engine 的"可解释文风分析"理念**——不依赖黑盒 Embedding，用 44 个可解释的中文表层统计特征做文风匹配，检索结果附带分项评分和理由。这在开源 AI 写作工具中很少见。

2. **Style RAG 的"文风而非知识"用法**——传统 RAG 检索世界知识注入上下文，这里检索写作风格注入二次改写指令。且只取当前 chunk 原文注入，不用摘要，保持文风原貌。

3. **"零向量数据库"架构**——4000×1024 float32 矩阵纯 NumPy 计算，存 SQLite BLOB。不引入 FAISS/Chroma/Milvus，PyInstaller 打包体积可控，不触发杀软误报。

4. **"零 SDK"LLM 通信**——用标准库 urllib 统一实现 OpenAI 兼容协议，8 家厂商零额外依赖，协议差异在 LLMAdapter 集中管理。

## Q11：如果让你继续迭代这个项目，下一步会做什么？

**参考应答：**

按优先级排列：

1. **API Key 安全存储**：引入 Windows Credential Manager，通过 Tauri Rust 端存取，Flask 端不接触明文。解决用户每次打开要重新输入的体验问题。

2. **Style Engine 算法升级**：当前 44 个特征是 V1，后续可以加入"句式模板抽取"（不只是统计句长，而是识别"主谓宾+状语后置"这类结构模式）和"情绪曲线分析"（段间情绪变化趋势）。

3. **多人协作模式**：当前是单机工具。如果要做团队协作，可以加一个可选的同步层——但不是把数据库搬到云端，而是用 CRDT 或差量同步，保持本地优先架构。

4. **评测体系完善**：M13 的 Benchmark 还比较粗糙，后续可以引入更多中文文体类型（武侠、科幻、悬疑、纯文学），建立标准化文风匹配评测集。

5. **跨平台**：当前只支持 Windows。Tauri 本身跨平台，但 PyInstaller 打包的 Flask Sidecar 需要为 macOS/Linux 单独构建。WebView2 在 macOS 上对应 WKWebView，适配工作量不大。

**追问：为什么不考虑做云端 SaaS 版本？**

因为项目的核心价值主张就是"本地、隐私、可控"。如果变成 SaaS，用户数据上传到服务器，Style Engine 的本地分析优势就消失了——与其在云端算，不如直接用更强的 Embedding 模型。而且 AGENTS.md 明确规定"不得擅自把项目改造成 Web、SaaS、远程服务或自托管平台"。这是一开始就确定的产品边界。
