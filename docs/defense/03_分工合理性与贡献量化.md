### 2.2 各阶段详细规划

#### 阶段 1：MVP 原型搭建（7/31 – 8/2，3 天）

| 维度 | 内容 |
|------|------|
| **目标** | 跑通"模板管理 → 提示词拼装 → LLM 生成 → 结果展示"最小闭环 |
| **产出** | `app.py`(66行) + `config.py`(187行) + `database/models.py`(179行) + 基础路由 + 首页模板 |
| **提交** | 5 次（4d16ca5 → 4f69ca8） |
| **验证标准** | 浏览器 `127.0.0.1:5000` 能完成一次完整的文章生成 |
| **时间占比** | ~15% |

> **合理性论证**：3 天搭建 MVP 是合理的——第一天搭骨架（Flask + SQLite + 基础路由），第二天补数据模型和种子数据，第三天打通生成链路。过早追求架构完善会拖慢"验证可行性"的速度。

#### 阶段 2：桌面化转型（8/3 – 8/7，5 天）

| 维度 | 内容 |
|------|------|
| **目标** | 从浏览器 Flask Demo 转型为 Tauri 2 桌面应用，并扩展 LLM 接入 |
| **产出** | `src-tauri/` Rust 桌面壳 + `flora-server.spec` PyInstaller 打包配置 + Gemini 中转支持 + Dockerfile + 版本信息 |
| **提交** | 4 次（a262017 → 64f067b） |
| **验证标准** | `cargo tauri dev` 可在 Windows 桌面窗口中加载应用 |
| **时间占比** | ~24% |

> **合理性论证**：这是全项目最大的架构决策点，用了最多时间（5 天）。从 Web 到桌面的转型涉及：Tauri 项目初始化（Rust 环境 + 前端嵌入）、Sidecar 模式设计（Flask 作为子进程）、PyInstaller 打包（`flora-server.exe`）、Gemini API 适配。每个子任务都有独立的学习成本，不能压缩。

#### 阶段 3：Style RAG 风格语料库（8/8 – 8/9，2 天）

| 维度 | 内容 |
|------|------|
| **目标** | 实现风格语料库导入 + 相似度检索 + 生成时注入匹配片段 |
| **产出** | `style_rag_service.py`（591 行，单文件最大） + `style_corpora_routes.py`（169 行） + 数据库迁移 + 前端交互 |
| **提交** | 2 次（79496e4 → 68fb481） |
| **验证标准** | 导入语料后，生成时自动检索 Top-3 文风匹配片段注入 Prompt |
| **时间占比** | ~10% |

> **合理性论证**：2 天完成 760 行核心逻辑，节奏快但合理——因为 Style RAG 的算法设计在阶段 2 已有腹稿，落地主要是编码 + 调试。关键是首次引入了 `prompt_assembler.py` 的大幅扩展（+158 行），将风格片段注入逻辑融入生成链路。

#### 阶段 4：架构重构与加固（8/10 – 8/13，4 天）

| 维度 | 内容 |
|------|------|
| **目标** | 消除早期 MVP 的技术债，统一分层，加固安全和稳定性 |
| **产出** | 路由层重构（`generation_routes` / `template_routes` / `style_routes` 拆分） + `operation_guard.py` 操作守卫 + LLM 适配层扩展 + 前端 Bug 修复 |
| **提交** | 5 次（822c087 → b452ed2） |
| **验证标准** | Ruff 检查通过，前端各功能流程无报错 |
| **时间占比** | ~19% |

> **合理性论证**：在功能基本跑通后做一次"还债式重构"是正确的节奏——如果拖到后期再做，改动范围会更大、回归风险更高。4 天用于：分层规范化、安全加固（API Key 不落盘链路完善）、模型厂商扩展（8 家适配）、前端交互打磨。

#### 阶段 5：Style Engine 本地文风引擎（8/14 – 8/16，3 天）

| 维度 | 内容 |
|------|------|
| **目标** | 实现纯本地中文文风分析器，44 个统计特征 + 余弦相似度检索，不依赖远程 Embedding |
| **产出** | `style_feature_service.py`（480 行） + 5 篇 Style Engine 设计文档 + 基准测试框架 + 导出脚本 + 测试套件（321 行） |
| **提交** | 4 次（944578d → ba57fd3） |
| **验证标准** | `pytest tests/test_style_feature_service.py` 全部通过，CSP 头放宽以支持 CloudStudio 预览 |
| **时间占比** | ~14% |

> **合理性论证**：3 天完成 480 行核心算法 + 1700 行文档 + 713 行测试 + 基准框架，是全项目技术密度最高的阶段。之所以放在阶段 4 重构之后，是因为 Style Engine 需要复用已重构好的分层架构（services 层），且需要数据库迁移机制已经稳定。

#### 阶段 6：收尾与发布（8/17 – 8/20，4 天）

| 维度 | 内容 |
|------|------|
| **目标** | Bug 修复、文档完善、版本号管理、发布准备 |
| **产出** | 最终修复提交 + README 完善 + 版本信息更新 |
| **提交** | 2 次（f923907 → 04ec5fc），8.21 正式发布 v1.0.0 |
| **验证标准** | 桌面 EXE 双击可运行，核心功能全部可用 |
| **时间占比** | ~18% |

> **合理性论证**：最后 4 天留给收尾是必要的——单人项目最大的风险是"功能写完了但没测完"。这段时间主要用于：端到端走查、文档与代码一致性检查、打包验证。

### 3.2 工具选型理由

| 对比维度 | Trae + DeepSeek V3 Pro | VSCode + Codex |
|---------|----------------------|----------------|
| **定位** | AI 原生 IDE，对话即编码 | 传统 IDE + AI 插件 |
| **模型** | DeepSeek V3 Pro（国产大模型） | Codex（OpenAI） |
| **优势** | 中文语境理解强、生成质量高、上下文窗口大 | 生态成熟、插件丰富、集成 Linter |
| **本项目用途** | 编写 80% 以上的业务代码 | 代码审查、文档校对、Debug 辅助 |
| **成本** | Trae 内置，无额外 API 费用 | Codex 免费额度 + 部分自费 |

> **选型逻辑**：DeepSeek V3 Pro 在中文代码注释和中文业务逻辑理解上有天然优势（本项目是中文创意写作工具），且 Trae 的 AI 原生体验（Cursor Like）使得"描述需求 → 生成代码 → 微调"的工作流极为流畅。VSCode + Codex 作为辅助，利用其成熟的 Linter 集成和 Ruff 配置做质量把关。

### 3.4 典型 Vibe Coding 工作流

以下是一个**真实模拟**的 Vibe Coding 会话（以 Style RAG 模块为例）：

```
━━━ 会话 1：需求描述 ━━━
开发者（Trae）：
  "我要做一个风格语料库功能。用户可以导入 txt 格式的参考文章，
   系统把它分句、分词、建索引。生成文章时，自动检索 3 个最相似的
   文风片段，拼到提示词里。用 SQLite 存，不要引入向量数据库。"

DeepSeek V3 Pro：
  → 生成 style_corpora_routes.py（导入/列表/删除 API）
  → 生成 style_rag_service.py（分句 → jieba 分词 → TF-IDF → 余弦相似度）
  → 在 prompt_assembler.py 中新增 style_context 注入点
  → 生成 database/migrations.py 迁移脚本

━━━ 会话 2：调试修正 ━━━
开发者（VSCode）：
  "导入一个大文件后检索很慢，看一下哪里是瓶颈。"

Codex：
  → 定位到 jieba 分词在每次检索时重复执行
  → 建议在导入时预计算分词结果并缓存到 SQLite

开发者（Trae）：
  "按这个建议改，把分词结果预计算后存到 corpus_tokens 字段。"

DeepSeek V3 Pro：
  → 修改导入逻辑，新增 tokens 序列化存储
  → 检索时直接读取预计算 tokens，跳过重复分词
  → 性能提升 ~10 倍
```

## 四、项目结构分配合理性

### 4.1 模块划分与开发顺序

项目采用**自底向上**的构建策略——先数据层，再服务层，最后路由和前端：

```
开发顺序（由内向外）：

  ① 数据层 ──────────────────────────────────────────────
     database/models.py    → ORM 模型（8 张表）
     database/migrations.py → 幂等迁移
     database/seed.py      → 预设模板数据

  ② 服务层 ──────────────────────────────────────────────
     services/api_client.py      → LLM 适配层（8 家厂商）
     services/generation_service.py → 生成编排
     services/prompt_assembler.py   → 提示词拼装
     services/style_rag_service.py   → 风格检索（阶段3）
     services/style_feature_service.py → 文风分析（阶段5）
     services/operation_guard.py     → 并发守卫

  ③ 路由层 ──────────────────────────────────────────────
     routes/generation_routes.py     → 生成 API
     routes/template_routes.py       → 模板 API
     routes/style_routes.py          → 风格 API
     routes/style_corpora_routes.py  → 语料库 API

  ④ 前端层 ──────────────────────────────────────────────
     templates/index.html    → 单页应用入口
     static/js/main.js       → 核心交互
     static/js/generation.js → 生成面板
     static/js/editor.js     → Markdown 编辑器
     static/js/style_rag.js  → 风格管理
     static/css/style.css    → 全局样式

  ⑤ 桌面壳 ──────────────────────────────────────────────
     src-tauri/src/lib.rs    → Rust 入口
     flora-server.spec       → PyInstaller 打包
```

### 4.2 结构合理性分析

| 维度 | 评估 | 说明 |
|------|------|------|
| **分层清晰度** | 优 | routes → services → database 三层分明，无跨层调用 |
| **模块内聚** | 优 | 每个 service 文件单一职责（生成、拼装、检索、分析、守卫） |
| **耦合度** | 良 | services 间通过函数调用耦合，无循环依赖 |
| **可测试性** | 优 | 20 个测试文件覆盖关键路径，Style Engine 有独立基准框架 |
| **可扩展性** | 良 | 新增 LLM 厂商只需在 `api_client.py` 加一个适配函数 |
| **前端工程化** | 中 | 原生 JS 无框架，但模块化拆分合理，适合桌面工具规模 |

> **结构决策说明**：选择"Flask 单服务 + 原生 JS"而非"React/Vue + API"分离架构，是因为 Flora_Editor 是本地桌面工具——前端页面和 API 由同一端口提供，天然无跨域问题，且打包体积更小（不需要 Node.js 运行时）。Tauri 的 Rust 壳仅负责启动 Flask Sidecar 和窗口管理，保持极简。

## 六、模拟答辩问答

### Q1：你是一个人做的项目，怎么保证 21 天能完成这么多功能？

**回答要点**：

核心策略是 **"AI 驱动 + 阶段递进 + 先验证后优化"**。

第一，AI 辅助编程将编码效率提升了 3-5 倍。Trae + DeepSeek V3 Pro 负责生成 80% 以上的业务代码，我集中精力做架构决策和逻辑审查。比如 Style RAG 的 591 行核心逻辑，用 AI 辅助从设计到可运行只花了半天，传统手写至少要 2-3 天。

第二，严格分阶段递进。21 天分 6 个阶段，每个阶段有明确的交付目标和验收标准。MVP 阶段 3 天先验证"能不能跑通"，桌面化 5 天解决"能不能交付为桌面应用"，后续每个阶段都在前一阶段基础上增量推进，不做回头返工。

第三，技术选型保守。Flask 单服务 + 原生 JS + SQLite，没有引入 React/Vue/向量数据库等额外复杂度，节省了大量环境配置和框架学习时间。Tauri 的 Rust 壳只有 177 行，因为大部分逻辑在 Python 侧。

### Q2：AI 生成的代码你怎么保证质量？

**回答要点**：

三道质量防线：

1. **人工审查**：所有 AI 生成代码我都会逐行阅读，重点检查业务逻辑正确性（如 API Key 是否落盘、SQL 是否有注入风险、并发是否有竞态）。
2. **工具交叉验证**：用 VSCode + Codex 做第二视角审查，它经常能发现 Trae 生成代码中的命名不规范、异常处理缺失等问题。
3. **测试驱动**：20 个测试文件、3,365 行测试代码，Style Engine 甚至有独立的基准测试框架。关键模块（生成链路、文风分析、语料检索）都有对应测试。

另外，项目规范（AGENTS.md）要求"算法变化必须新增测试"，这个约束倒逼我在 AI 生成代码后立即补测试。

### Q3：你说的 Vibe Coding 具体是什么工作模式？

**回答要点**：

Vibe Coding 的核心是 **"用自然语言描述意图，AI 生成代码，人类审查和微调"**。

以 Style RAG 模块为例，我的工作流是：

1. **口述需求**：在 Trae 中用中文描述"我要做一个风格语料检索功能"，包含输入/输出/存储/约束。
2. **AI 生成骨架**：DeepSeek V3 Pro 生成完整的路由 + 服务 + 数据库迁移代码。
3. **人工审查**：逐行读代码，发现逻辑问题（如分词重复计算）后，回 Trae 描述修正需求。
4. **调试验证**：用 VSCode + Codex 定位性能瓶颈，再回 Trae 让 AI 优化。
5. **测试补全**：让 AI 生成测试用例，人工补充 Edge Case。

这个循环中，我的角色是"产品经理 + 代码审查者"，AI 是"高级码农"。我不写代码，但我读每一行代码。
